# 可配置投资监控与风险雷达

把自然语言关注点转换为可检查、可修改、可暂停、可解释的长期监控任务。产品不预测涨跌，不提供买卖、目标价或仓位建议。

## 目标用户

- **有明确关注点但无法持续盯盘的个人投资者**：例如「茅台跌破 1400 提醒我」「贵州茅台进入热榜前十」。「他们要的不是行情看板，而是」我关心的事发生了没有。
- **需要可追溯解释的谨慎用户**：不满足于收到一条推送，而要知道**为什么触发、为什么没触发、依据是哪个字段、哪个时点、哪次请求**。
- **明确不适合**：寻求涨跌预测、买卖建议、目标价或仓位建议的人。本产品不提供这些。

## AI 角色

| 环节 | AI 是否参与 | 说明 |
|---|---|---|
| 自然语言 → 规则草案 | ✅ 受限解析 | 从自然语言中抽取条件类型、标的、比较方向、阈值、关键词、检查频率与冷却时间，生成**可编辑的规则草案** |
| 规则生效 | ❌ | 草案必须经用户查看、修改并确认后才创建任务，AI 不能自行启用 |
| 条件判定 | ❌ **刻意不用模型** | 价格比较、排名比较、关键词匹配、日期校验、冷却与去重全部由确定性代码执行 |
| 证据与数字 | ❌ | 价格、成交量、排名、异动标签、行情日期均为接口原值，模型不得补写或改写 |
| 原因解释 | ⚠️ 模板化 | 由 `reason_code` 驱动固定文案，不是模型自由生成 |

**为什么判定环节刻意不交给模型**：监控产品的核心价值是「可复现」——同一份数据在任意时刻应得到同一结论，且该结论能被追溯回原始字段。模型输出不具备这种确定性。因此 AI 只用于**降低表达成本**（把一句话变成结构化规则），不用于**决定结论**。

开发过程中的 AI 使用情况见 `AI_USAGE_AND_VALIDATION.md`。

## 已实现的主链路

自然语言 → 受限解析器生成规则草案 → 用户检查和修改 → 创建任务 → 定时/手动检查扶摇真实数据 → 确定性判定 → 保存证据和解释。

**统一任务模型的四类条件均已真实接通并实测：**

| 条件类型 | 数据源（扶摇） | 判定语义 | 实测结果 |
|---|---|---|---|
| `price` 价格 | `/api/a-share/prices/snapshot` + 历史日 K 线 | 最新价 高于 / 低于 阈值 | ✅ 600519.SH = 1240.99 元 |
| `heat` 热度 | `/api/a-share/special-data/hot-stock-list` | 进入热股榜前 N 名 | ✅ 榜内 30 条 |
| `event` 事件 | `/api/a-share/special-data/anomaly-analysis-list` | 个股异动标签 / 关键词命中 | ✅ 异动列表 175 条 |
| `calendar` 日历 | `/api/a-share/calendar/trading-days` | 今日 是 / 非交易日 | ✅ 242 个交易日 |

- 任务暂停 / 恢复 / **归档**（只收纳、不删除，历史与版本完整保留，可恢复启用）、立即检查、规则编辑与版本历史
- 触发、未触发、冷却、去重、非交易日跳过、降级、失败、数据受限、**数据冲突**，九种语义互不混淆
- 失败自动退避重试：仅对瞬时故障重试，凭证类错误立即返回，证据链记录实际尝试次数
- 去重按「任务 + 版本 + 交易日 + 条件」计算：同一交易日不重复提醒，**跨交易日可再次触发**
- 检查记录关联任务、规则版本、运行方式、耗时、来源与 `request_id`
- 每条证据标注数据时点及其来源（`asOfSource`：K 线日期 / 接口时间戳 / 交易日历 / 接口未提供）
- 服务重启后从本地 JSON 恢复，且任何 HTTP 请求都会触发一次到期补跑
- 接口失败、数据时点不可确认、多源数据时点冲突或日期不可验证时，都不会输出“未触发”
- **恢复可追溯**：任务详情页有「运行状态」块，展示最近成功检查、最近异常、恢复时间与恢复处理；暂停后恢复、归档后重新启用、接口故障恢复、服务重启恢复、错过计划补跑、数据源恢复后重查分别成类，每条恢复处理都写明「未产生重复提醒」
- **触发即通知**：桌面通知（浏览器）与微信推送（服务端出站：企业微信 / Server 酱 / PushPlus / 自定义 Webhook）；冷却与去重语义在推送侧同样生效

## 产品边界：明确拒绝预测与荐股

不预测涨跌、不提供买卖与仓位建议，这不是「暂未实现」，而是**刻意划定的边界**。关键在于拒绝的方式：早期版本对「帮我预测茅台明天涨跌」会返回「请输入价格阈值」——那会让人以为**只差几个数字没填完**，从而把一条本不存在的路径误当成可用功能。现在系统在解析前就明确拒绝，并给出可执行的替代写法。

| 意图 | 典型输入 | 返回文案 |
|---|---|---|
| 预测涨跌 | 帮我预测茅台明天涨跌 / 明天会涨吗 / 帮我看看走势 | 本产品不预测未来涨跌。你可以创建基于真实数据的价格、热度、事件或交易日历监控。 |
| 买卖与仓位 | 建议我买入贵州茅台 / 帮我满仓 / 该清仓吗 | 本产品不提供买卖和仓位建议。你可以设置可验证的观察条件，由系统持续检查并展示依据。 |
| 其他投资建议 | 茅台值得投资吗 / 帮我推荐一只股票 | 本产品不预测股票涨跌，也不提供买卖、仓位或收益建议。你可以把关注点改成可验证的监控条件，例如「贵州茅台跌破 1400 元时提醒我」。 |

- **两档识别，避免误伤合法监控**：强信号词（预测、满仓、荐股等）在解析之前直接拒绝；弱表达**只在正常解析失败之后**才判定。这样「贵州茅台会不会跌破 1400」这类既像提问、又是合法监控诉求的句子仍能正常解析成规则，不会被误拒。
- **拒绝不是报错**：界面用中性说明样式呈现，不显示「请输入价格阈值」这类把人引向错误方向的提示，也不会渲染出一份看似可提交的草案。
- **每条拒绝都附替代写法**：文案下方提供「填入替代写法」按钮，一键填入类似 `贵州茅台跌破 1400 元时提醒我` 的合法条件。
- 该层边界由 `test/guardrails.test.js` 的意图识别用例断言覆盖。

## 组合条件（AND / OR）

「茅台跌破 1400 **并且**进入热榜前 10」这类复合关注点是真实需求。当前版本已支持把多个子条件组合成一个任务：

- **可解析**：`parseRule` 识别 `并且 / 且 / and`（AND）与 `或者 / 或 / or`（OR），生成 `{ kind: 'composite', logic, conditions: [...] }`；**同一句里混用 AND 与 OR 会被明确拒绝**，并提示拆分，不猜测优先级。
- **可创建、可编辑**：规则草案与编辑弹窗都有结构化子条件编辑器（增删行、逐行选类型 / 标的 / 操作符 / 阈值、切换 AND / OR），不要求用户手写 JSON。
- **标的继承**：后一个子条件省略标的时继承前一个子条件的标的（「茅台跌破 1400 并且进入热榜前 10」⇒ 两个子条件都是 `600519.SH`）。
- **逐子条件求值、整体合并**：每个子条件独立取数、独立判定，证据里**每个子条件单独一行**，并给出「组合逻辑 / 子条件 / 组合结果」三段。
- **降级不强行判定**：任一子条件处于「数据不可用」或「数据受限」时，整体状态为 `degraded`，结论为「不强行判定」——绝不会用一个残缺的子条件集去算出一个看起来完整的结论。这条与「异常不得折算为未触发」是同一根红线。
- **频率取最保守值**：检查间隔取子条件中的最小值，冷却时间取最大值。

## 数据新鲜度设计

扶摇快照的 `data.timestamp` 是接口抓取时刻，不等于行情日期，不能直接用于过期判断。本项目采用：

1. 交易日历确定最近交易日；
2. 历史日 K 线最后一根 `date_ms` 作为行情日期锚点；
3. 若最后 K 线日期落后于最近交易日，返回 `degraded / DATA_STALE`，暂停条件判定；
4. 界面分别展示抓取时刻和行情日期。

### 热度数据时点：三态，且禁止「时点不可用 + 未触发」并存

热股榜接口的 `data.timestamp` 是**抓取时刻**，不是榜单业务时点。把抓取时刻当作业务时点，等于用一句含糊的话给用户一个结论。因此热度判定区分三种情形，且**措辞强度跟着数据强度走**：

| 情形 | 状态 | 证据写法 |
|---|---|---|
| 数据源提供榜单业务时间 | 未触发 | 「贵州茅台未进入 2026-09-30 10:30 获取的前 30 名榜单」 |
| 只有本次抓取时间 | 未触发 | 「本次获取的前 30 名榜单中未找到贵州茅台 / 榜单业务时间：数据源未提供 / 获取时间：… / 可信度提示：仅能确认本次获取结果，无法验证榜单所属业务时点」 |
| 两者都不可用 | **数据受限** `restricted` | 结论为「本次未执行条件判断」，原因「榜单业务时间不可用」 |

> **红线**：「数据时间不可用」+「未触发」这个组合**不允许出现**。无法确认数据属于哪个业务时点时，系统不给结论——`restricted` 是独立状态，既不并入「未触发」，也不并入「失败」。

当前热股榜的真实落点是第二种（只有抓取时间）：`provider.js` 中 `datasetTime` 恒为 `null` 并附注说明，一旦数据源提供业务时点即可自动升级为第一种；`asOfSource` 随之标记，界面如实展示而不推测。该红线与三态分支由 `test/guardrails.test.js` 断言覆盖。

### 多源数据时点冲突：两份数据打架时，不挑一份顺手的用

价格条件同时依赖两份数据：实时快照（`last_price`）与历史日线（最新收盘 `close`）。两份数据的业务时点必须能归入同一条时间线（盘中：快照 = 今日盘中、日线 = 上一交易日；非盘中：两者同为最近收盘日）。一旦归不进同一条时间线，系统记为**数据存在冲突**（`conflict` / `DATA_CONFLICT`），输出四行结论：

- 状态：数据存在冲突
- 结果：本次未执行条件判断
- 原因：实时快照与日线数据所属时点不同（写明两份数据各自的业务时点）
- 建议：等待下一次检查或手动重试

**判据是「时点不自洽」，不是「数值不一致」**：盘中快照 1398 元、昨收 1412 元完全正常，把数值差异当冲突会让系统天天报警。当前判据只有两条「绝不该发生」的硬矛盾——快照业务时点早于日线最新 bar（快照比日线还旧）、日线日期晚于今天（未来数据），因此不会误伤正常交易时段。README 与界面口径里的演示场景（快照 2026-09-29 14:55 报 1398.00 元、日线 2026-09-30 收盘 1412.00 元）已固化为 `test/conflict.test.js` 的可重复用例。

### 任务归档与恢复叙事

**归档只收纳、不删除。** 这是审计型产品的取舍：记录本身就是产物，永久删除会让「曾经监控过什么、当时看到了什么」无法回溯。归档后任务不再进入调度（`nextRunAt` 为空、手动检查返回 409），但版本历史、检查记录与判定证据完整保留，随时可恢复启用；界面提供归档按钮与「运行中 / 已暂停 / 已归档」筛选。

**恢复不是一个状态，而是一段过程。** 只写「现在正常」说服不了评审。任务详情页的「运行状态」块把恢复拆成可追溯的事件：最近成功检查、最近异常（含原因）、恢复时间、恢复处理，以及最多 20 条恢复历史。恢复分七类（暂停后恢复 / 归档后重新启用 / 接口故障恢复 / 服务重启恢复 / 错过计划补跑 / 数据源恢复后重查 / 降级解除后重查），**每一条的恢复处理都写明「未产生重复提醒」**——恢复后的检查仍走同一套去重与冷却逻辑，不会因为「刚恢复」就补发一次通知。分类与记录逻辑独立在 `recovery.js`，由 `test/recovery.test.js` 逐条断言。

## 界面可靠性设计

服务端不静默，界面同样不能静默。以下三条来自一次真实事故（2026-09-30）：**所有接口都返回 200，页面却永久停在「正在检查数据服务状态…」**——根因是 `index.html` 里的 `<script>` 位置早于它要绑定的 DOM，脚本顶层对 `null` 赋值抛错，后续绑定与首次刷新全部中断。

1. **脚本位置**：`app.js` 置于 `</body>` 之前，确保绑定时所有元素已存在；由 `test/frontend.test.js` 断言。
2. **绑定安全**：所有事件绑定走 `on()` 包装，元素缺失时记录告警并跳过，不再让单点缺失中断整页。
3. **失败可见**：`boot()` 与全局 `error` / `unhandledrejection` 监听都会把异常写入状态横幅；`fetch` 带 20 秒超时。**初始化失败时显示具体错误，而不是永远停在「正在检查」。**
4. **构建版本**：`index.html` 以 `/app.js?v=<版本>` 引用脚本，版本号由服务端根据 `app.js` / `style.css` 的修改时间自动生成，HTML 本身以 `Cache-Control: no-store` 提供。这避免了 CDN 或浏览器缓存旧脚本、与新页面混用后整页失效。

## 界面使用说明与筛选

页面顶部「产品说明书」板块**整体可折叠**，内含三个子块，全部用原生 `<details>` 实现（脚本异常时依然可用）：

- **使用操作指南**：三步上手流程与操作注意点。
- **逻辑规则**：四类条件与组合条件（AND / OR）的判定方式、默认频率与冷却（组合取子条件中最保守的值）、状态机（含「数据受限」与「数据冲突」）、去重与冷却语义、**任务归档（只收纳、不删除）**、参数边界。
- **指标口径说明**：各条件取哪个接口、关键字段、`as_of` 的取法（含热榜数据时点的三态口径与价格多源时点冲突的判据、复现用的演示场景），以及降级与非交易日口径。其中如实标注了预留但**尚未生效**的 `DATA_STATIC` / `SCHEMA_MISMATCH`，不把没实现的东西写成已实现。

检查记录区域提供**筛选器**（查看任务 / 时间区间 / 结果 / 条件类型 / 重置），每条记录**可折叠**：收起时显示状态、`reason_code`、条件类型与一句话原因；展开后给出任务、无结论状态专用的「结果 / 原因 / 建议」三行、数据情况、原始字段（含 `request_id`、`as_of`、尝试次数）与异常诊断，便于截图留证。筛选只做过滤，不改动原始记录；展开状态在刷新后保持。任务列表提供「全部 / 运行中 / 已暂停 / 已归档」筛选，顶部统计区分运行中、已暂停与已归档。

## 通知与提醒

「触发之后用户怎么知道」是监控类产品最容易被追问、也最容易被含糊带过的一环。本项目提供两条职责互补的通道：

| 通道 | 走向 | 覆盖场景 | 配置成本 |
|---|---|---|---|
| ① 浏览器桌面通知 | 浏览器 → 系统通知 | 页面开着（含后台标签页） | 零，浏览器授权一次即可 |
| ② 微信推送 | 服务端 → 企业微信 / Server 酱 / PushPlus | **页面关掉也能收到** | 需要使用者自己的机器人地址或 Key |

- **只在判定为「已触发」时推送**：冷却中与已去重的语义本身就是"同一天已经提醒过了"，再推等于绕过去重、把提醒变成骚扰。
- **推送失败不影响检查**：所有异常在 `notifier.js` 内消化为失败结果，绝不因此让检查失败或丢记录；失败原因写入记录便于排查。
- **凭证安全**：渠道凭证保存在运行时状态（`data/state.json` 已在 `.gitignore` 中排除），读取接口只返回脱敏形态（如 `••••a1b2`），编辑时前端显式声明 `keepTarget` 表示"凭证未改动"；凭证同样不进 URL（PushPlus token 走载荷），避免被日志与浏览器历史留痕。
- **如实说明局限**：桌面通知依赖浏览器，页面关闭即失效——这正是需要服务端微信推送的原因；微信推送的端到端投递需要使用者自己的凭证，页面「测试全部已启用渠道」按钮即为此准备。

企业微信机器人在群聊「… → 添加群机器人」即可免费获得 Webhook 地址（无条数限制）；推送到个人微信可选用 Server 酱（sct.ftqq.com）或 PushPlus（pushplus.plus）。

## 状态与原因编码

| 状态 | 典型 reason_code | 含义 |
|---|---|---|
| triggered | CONDITION_SATISFIED | 条件首次满足 |
| not_triggered | CONDITION_NOT_MET | **数据有效**，但条件未满足 |
| cooldown | COOLDOWN_ACTIVE | 条件持续满足但仍在冷却期 |
| deduplicated | DUPLICATE_SUPPRESSED | 同一交易日内已提醒，抑制重复 |
| skipped | NON_TRADE_DAY | 非交易日跳过判定，**不计为失败** |
| degraded | DATA_STALE / DATA_STATIC / RATE_LIMITED / SCHEMA_MISMATCH / CAPABILITY_DISABLED | 数据不可信或不可得，暂停判定 |
| **restricted** | **DATA_RESTRICTED** | **数据时点不可确认**，明确声明「本次未执行条件判断」 |
| **conflict** | **DATA_CONFLICT** | **多源数据业务时点互相矛盾**（如实时快照与日线所属时点不同），不挑一份用，声明「本次未执行条件判断」并建议等待或重试 |
| error | SOURCE_ERROR / AUTH_INVALID / FIELD_MISSING / TICKER_NOT_FOUND | 接口、凭证或字段异常 |

> **红线**：`degraded`、`restricted`、`conflict` 与 `error` 在任何聚合统计和任何界面文案中都不会被折算为 `not_triggered`，也不会显示为“正常”；冲突文案不得携带「条件满足 / 未满足」这类结论性措辞。该规则由测试断言强制——`test/engine.test.js` 的红线用例覆盖「四类条件 × 五类异常」共 20 种组合，`test/guardrails.test.js` 覆盖「热度时点不可用」与「组合条件子条件降级」，`test/conflict.test.js` 覆盖「冲突不得输出触发 / 未触发」「数值差异不等于冲突」与「组合条件子条件冲突」。

## 线上部署与数据持久化

线上示例：<https://invest-radar.app.workbuddy.host/>（单端口 HTTP 服务，服务监听 `PORT` 环境变量）。

状态文件只有一份：`data/state.json`，**任务、检查记录、通知渠道凭证都写在里面**。

⚠️ **发布是「整个目录上传」，会把本机的 `data/state.json` 一并覆盖到线上。** 已实测：发布后线上记录数与本机完全一致。由此带来一个必须知道的后果——

> 如果你已经在线上配好了推送渠道凭证，**之后再重新发布，线上配置会被本机那份覆盖（凭证随之丢失）**，需要重新粘贴一次（页面「添加渠道」+「测试全部已启用渠道」，约一分钟）。

发布前的自检建议：

1. 确认本机 `data/state.json` 里没有你不想带上去的本地调试数据（**要发布一个干净实例，就把该文件重置为 `{"tasks":[],"runs":[],"settings":{"notify":{"channels":[]}}}` 再发布**）；
2. `data/state.development-backup.json`（开发期快照）不参与运行，但会被整目录上传。要发布干净实例，把它**临时移出项目目录**、发布完成后再放回（静态服务只暴露 `web/` 下三个文件，`data/` 不对外可达，此举属额外整洁措施）；
3. 发布后重新检查线上渠道是否仍在，不在就重配；
4. 想验证真实投递，用页面上的「测试全部已启用渠道」按钮，不要只看界面文字。

> 注意：改完 `data/state.json` 要**先停服务再改文件**。服务进程把状态常驻内存并按需写回，边跑边改文件会被内存里那份覆盖掉。

平台沙箱为临时文件系统，实例重启后状态可能丢失（进程启动时会补跑到期任务）。

## 当前边界

- 已真实运行的条件类型为**价格、热度、事件、日历**四类，以及由它们组成的**组合条件（AND / OR）**；组合条件支持 2–5 个子条件，**暂不支持子条件嵌套，也不支持同一句里混用 AND 与 OR**（这两种写法都会被明确拒绝并提示拆分，而不是猜一个优先级）。
- 热股榜未提供可信的业务时点（接口 `data.timestamp` 是抓取时刻），因此其判定走「只有抓取时间」这一档：结论照常给出，但证据里写明业务时间缺失与可信度边界；一旦时点完全不可用则转为「数据受限」而不给结论。
- 事件条件由「个股异动原因」驱动，**不是**新闻 / 公告语义——资讯事件接口对当前凭证返回 `code=2004`（未开放）。
- **停牌标的无法与「不存在标的」区分**：扶摇对两者都可能返回 `1002`，系统按「规则不可执行」处理并提示修改。
- 本地 JSON 适合单用户演示，不是生产级多用户存储；公网部署若使用临时文件系统，重启后可能丢失状态（进程启动时会补跑到期任务）。
- 定时调度依赖服务进程保持运行；免费平台休眠期间不会持续检查，被唤醒后按「补跑」处理并在记录中标注。
- 暂无登录与多用户隔离。
- 桌面通知依赖页面保持打开（后台标签页可用）；**微信推送的端到端投递尚未用真实凭证验证**（验收用本地接收端代替，页面「测试」按钮用于接入真实渠道后自查）。

## 未做事项（明确未实现，不宣称已完成）

1. **组合条件的深层能力**：已支持 2–5 个子条件的 AND / OR 组合，但**不支持嵌套**（组合里再套组合），也不支持同句混用两种逻辑；未提供组合条件的真值表预览与命中历史统计。
2. **生产级持久化**：仍为单进程 JSON 文件，未替换为 Postgres；公网平台重启后状态可能丢失（启动时补跑）。
3. **离线推送**：桌面通知依赖页面打开；要做到浏览器关闭后仍推送，需要 Service Worker + Web Push（含 VAPID 与推送服务），当前版本未实现——现实可行的替代是服务端微信推送（已实现）。
4. **多用户与权限**：无登录、无数据隔离，任何人可查看和修改全部任务。
5. **LLM 解析通道**：自然语言解析当前为确定性受限解析器，未接入大模型兜底通道。
6. **回测与模拟**：未提供规则历史回放、参数调优或命中率统计。
7. **移动端适配**：界面按桌面浏览器设计，未针对小屏优化。
